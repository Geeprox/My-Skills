01 / 先确定导入目标

个人学习词典和“常用语”，是两套机制。

本次真正打通的是按自然拼音参与候选竞争的个人学习词典。把“短码 → 文本”导入常用语，不能等价替代专业术语、人名或项目名的学习词典导入。

维度个人学习词典常用语 / 自定义短语
输入体验输入拼音，在普通候选中寻找目标词；顺序受匹配与历史状态影响。输入指定短码，展开固定文字或模板。
主要入口上屏学习事件；内部 UserDictV2::Add。设置页；“导入系统自定义短语”；UserHotWordDict::Import。
核心存储userDict/v5/<generation>，主中文词典 kind 128、命名空间 !v2u!。userDict/user_hot_word，独立容器。
导入所需词 + 明确的逐音节拼音；由原生引擎构造学习元数据。输入码 + 内容；不继承其他输入法的自然词频。
系统短语桥接仍然适合什么场景？

固定快捷回复可走“词表 → 系统短语 plist → macOS 自定义短语 → 微信导入系统自定义短语”。本机 2.2.3 的 UI 与静态函数均确认了该入口。系统导入 wrapper 曾观察到总量 1000、输入码前 8 个字符、内容前 2000 个字符等限制；它们只代表该构建的这条入口，不能推广成所有版本或底层 API 的永久限制。

这一桥接本次没有执行正式批量导入。公开资料与本机静态入口说明可行性，不能代替导入后的真实召回验收。

02 / 产生 → 记忆 → 召回

一次学习，涉及词条、索引和操作记录。

1真实上屏选择候选 / 连续输入
2筛选与记录单次 / 多次上屏处理
3原生 Add合并学习元数据
4持久化与索引LevelDB / 音节 / action
5拼音查询查词、过滤、评分
6候选与提交候选更新 / 实际上屏

产生：真实输入进入学习处理器。

静态链路包含 UserDictSingleEmitWrapper::onInputEmitted、UserDictMultipleEmitsWrapper，中文分支进一步进入 UpdateNormalUserDict → UpdateUserCnDictHelper::Add → AddWithCallBack。连续多次上屏还可能组合记录；潜在词典 kind 148 / !potential_ud! 与主词典 kind 128 是不同目标。[S1]

这说明“输入一次就必定学习”不是一个已证明的规则。粘贴、光标上下文、组合词过滤及潜在词提升阈值仍未完整恢复；本次导入器通过已验证的主词典 Add 路线添加显式词对。

记忆：计数、时间和匹配状态一起更新。

UserDictV2::Add(pinyin, word, option) 经读写层读取已有状态并合并记录，维护 Bloom filter、动态音节索引和相应操作日志。WordItemV2 内层为 48 字节元数据加词文本；不是只存一个裸词或一个整数“词频”。同词重复 Add 会更新学习计数，所以工具要先查重、跳过已有词对。[S1]

内层词记录的已确认序列化布局；不是给用户编写的导入格式

标记字节 0        LE uint16 词字节数      48B 元数据        UTF-8 词文本

一个 value 中可串联多条记录；外层还有命名空间与存储封装。

落盘：三个层面需要一起考虑。

词条事实

LevelDB + 命名空间

主个人词典 !v2u! 的拼音桶内存放一个或多个词记录。SST、WAL、MANIFEST 和 CURRENT 共同描述数据库状态。

查询路径

静态 + 动态音节索引

ReLoadIndex / LoadStaticIdx 与 MemBasedUserSyllableIdxDict 服务后续拼音查询。仅手写一个 value 不能证明索引同步。

变更轨迹

操作记录 !dcact!

原生 Add 产生有序 action；旧 action 被清理后，header 的累计序号仍保留。不能用现存 action 最大键推导下一条序号。

3.0 操作 header 解码后为 16B：保留字段 + 累计序号（均为 LE64）。底层存储值有逐字节 +6 与长度 / magic 尾部封装，不能把原始 LevelDB value 当作未封装结构解析。工具采用严格版本和精确变化校验；这些内部格式不是公开协议。[S2]

召回：存在词对，仍需要走完整候选链验证。

音节图和用户词搜索器负责查找匹配词，读写层提供词记录，过滤和评分综合历史、时间及匹配类别；最终还要与主词库、模型和其他搜索策略合并。完整评分公式和所有系数未恢复，不能承诺导入词永远排第一。

运行验证输入无分隔的连续全拼，逐个 ASCII 键调用 wxime_process_input，从候选回调取得迭代器并枚举；新进程再次查词和查候选，把“内存里可见”“已落盘”“新进程可召回”分开确认。正式 UI 验证则进一步检查按键后真正提交的文字。

05 / 把原生 Add 变成可审计导入

准备、验证、提交分开；候选查询也可能写数据。

最关键的修正：提交副本只执行 Add；召回验收放在另一个可丢弃副本。

完整会话查询会触发 CandidateCompletion::ExposureInfoWriteBack → UserPrefixDict::Update → UpdateExp，更新 !user_prefix2! 的曝光统计。最初完整 KV 审计发现两个既有前缀键变化，闸门拒绝写回。随后将“Add-only 待提交副本”和“召回验证副本”分开，保留候选验收而不把曝光副作用带回正式词库。[S2、P1]

  1. 校验与预览。

    输入词和明确的逐音节拼音；规范化格式，检查字段、字符 / 音节数、音节白名单与批量边界。按“规范化拼音 + 词”去重。同音不同词保留，已有词跳过；跳过时不调用 Add，不增加旧计数。预览固定词表和主词状态，主记录或元数据改变后计划失效；仅辅助日志 / 曝光统计变化可在新快照中保留。

  2. 正式退出并拿到正确的锁。

    先切到普通输入源，正常退出微信输入法；若未退出或自动重启则中止。使用与 LevelDB 实际锁兼容的 fcntl 记录锁，持有原数据库的 LOCK 文件锁后才复制。检查 PID 或 lsof 只能辅助观察，不能代替排他锁。

  3. 一致备份、受限副本添加。

    对完整 v5 目录做一致备份并核对逐文件摘要；引擎只在备份克隆内运行。目标代码加载前施加 OS sandbox，实测正式库读写、job 外写入、网络连接被拒绝。每词先查重、调用高层 Add 并等待完成。

  4. 全量语义与完整 KV 双重闸门。

    比较全部主词记录及元数据：只允许计划中新词增加、旧记录原样保持。再比较完整底层 KV，严格核对目标拼音桶、action header 及相应连续 action；不能只统计条数或忽略其他命名空间。每个新增 action 序号从旧 header 累计计数递增验证。

  5. 在另一个副本、新进程验证召回。

    克隆 Add-only 结果，重新初始化引擎，验证持久词对与实际连续拼音候选。验证副本即使生成曝光统计也不参与提交。目标未在枚举范围内出现或回调失败时拒绝该批；目标已出现而列表截断时，保留 truncated 标记，不把它解释为完整候选列表。

  6. 原子提交与失败恢复。

    确认正式 App 仍未重启、备份和变化闸门通过后，对旧目录和待提交目录持锁，用同文件系统 renamex_np(RENAME_SWAP) 交换；核对新旧两侧精确文件摘要并同步目录。失败时交换回旧目录并恢复输入法。没有原子交换能力时拒绝静默降级为多文件覆盖。

程序硬中断后：先查看状态，再恢复事务

"$SKILL_DIR/scripts/wetype" --workspace /私有路径/wetype-lab-formal --target formal recover 事务ID

事务日志在停止输入法前记录原运行状态与输入源，在交换前保存前 / 后摘要。普通异常尽可能自动换回旧库；硬中断后 recover 按当前库与已审核前 / 后状态分类，恢复输入法并标记提交或未提交，不盲目覆盖词库。无法判断时保留数据并拒绝继续；待恢复事务未关闭前，禁止新的 import / rollback。不要手动删除锁文件、日志或中间目录。
